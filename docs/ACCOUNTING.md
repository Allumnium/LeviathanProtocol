# Atomic accounting and checkpoints

Step 4 adds one run-scoped ledger and one checkpoint containing both the resulting state and the ledger. `commit_event(kind, source_id, credits_delta, material_delta, rp_delta, details, economy_after)` supports arrival, casualty, cargo sale, victory, ore pickup and enemy salvage identities. Event IDs are `run_id/kind/source_id`. Consumers must use stable node/component/pickup identities, not UI-open counts or timestamps. New runs receive a fresh run ID, even when replaying the same seed.

Replaying an identical event acknowledges it without paying again. Reusing an identity with different amounts/details/economic state is rejected. Entries record deltas, balances before/after and a normalized fingerprint. Credits may be negative; inventory and RP may not. Arithmetic is bounded to JSON's exact integer range. Optional `economy_after` lets future port/loss systems commit occupancy/cargo changes with the corresponding amounts and ledger, without first mutating live component state. Those actor/service rules remain in their scheduled milestones.

## Commit and recovery

`AtomicRunStore` writes a versioned envelope with generation, serialized payload and SHA-256 integrity check. It stages and flushes a complete `.next`, verifies it, then rotates the previous valid main file to `.bak` and promotes the staged file. The verified complete stage is the commit point. Recovery chooses the highest valid generation among main, `.next` and `.bak`; incomplete/corrupt files and semantically invalid payloads are ignored. A recovered stage is promoted before another stage can overwrite it. Replacing a corrupt main preserves an existing good backup. Generation checks reject stale writers.

Live amounts, economic state and ledger change only after durable staging succeeds. Signals fire after the corresponding live state is applied. A failed stage leaves the economic event retryable without applying amounts or consuming its identity. A process interruption after staging recovers the whole new state; an interruption before staging recovers the whole previous state. There is no separate balance write that can become detached from its deduplication record.

`RunCheckpoint` persists run metadata, signed credits, inventory, ledger, economic state, editor blueprint, physical fleet identities/formation/component HP, upgrades, the actual current graph/progression and any pending deployment's actual alien roster/stats. It validates and reconstructs the complete checkpoint before applying it. Live event commits preserve physical ship object references used by combat. Archive discoveries and archived blueprints remain separate files.

GameState saves automatically on new run, deployment, victory, withdrawal/failure settlement, and committed ledger events. `save_run_checkpoint()` is also available for explicit preparation checkpoints. `load_run_checkpoint()` loads a validated checkpoint/backup. These are backend methods; no new Continue menu or exact in-flight save loader is claimed. Preparation edits/purchases since the last checkpoint and unsaved combat ticks are outside this recovery boundary. Step 6 stores all frozen encounters; steps 8–9 add attempts, finite-field hooks, terminal defeat and settled command/event diagnostics. See BATTLE_LIFECYCLE.md.

Victory commits route advancement, credits and salvage together. The battle controller no longer refunds salvage through UI-driven per-drop balance changes. If saving fails, the controller retries settlement instead of marking the report complete. Step 6 now supplies the frozen reward progression described in ENCOUNTERS.md. Generic event hooks do not activate passengers, cargo, mining or RP-producing labs early.
