# Development thoughts

Questions, concerns and ideas recorded during development. These are observations and proposals, not an implementation backlog or approval to change gameplay. Agreed work belongs in [TODO.md](TODO.md); verified deliveries belong in [COMPLETED.md](COMPLETED.md).

## 2026-11-07 - Starting P2

- **Observation / content authority:** JSON is loaded through the new pack pipeline, but research grants are still filtered and rewritten in code. An inspector could show a valid edit that gameplay ignores. P2 should prove changes through real gameplay transactions, not only database lookups.
- **Concern / diagnostics:** Four focused suites have documented failures from before P1. Distinguish stale fixtures from gameplay defects before using them to assess refactors; otherwise a new regression could hide inside an accepted failure count.
- **UX proposal / explain an unavailable option:** The future inspector and Playtest overlay could show which prerequisite, equipment capability or rule prevents an option, with a jump to its definition. This would make valid-but-inactive content much easier to debug without hover tooltips.
- **Imaginative proposal / paired playtests:** A designer could compare the same seed and commands with and without a patch, highlighting changed encounters, prices and quest outcomes. This builds naturally on content hashes and stable streams; defer the surface until Playtest exists.
- **Refactor opportunity / cached content views:** GameDefinitions, SlotCatalog and ShipLoadouts keep independent static caches. When the editor reloads a pack, those caches can retain previous definitions. Tie cache lifetime to the loaded database or remove the duplicate caches as callers move to Content.
- **Question / starter package ownership:** Keep engine-wide equipment and fleet packages in core, but put the current campaign's selected starter package and resources in leviathan. This lets another scenario reuse the mechanics without inheriting the convoy charter. P2 can introduce a small start definition now; P6 can compose it into scenario recipes.
- **UX concern / misleading metadata:** Some authored ability and research definitions still describe retired or unavailable behavior. Do not expose those as usable options just because a generic Library form can display them. Make availability explicit while preserving current gameplay.

## 2026-11-07 - P2 starter and economy implementation

- **Resolved / starter package ownership:** Added `core:convoy` as a reusable fitted fleet package and `leviathan:charter` as the campaign's starting resources and dock. No new player setup controls are needed for this phase; P6 can expose starts through scenario recipes.
- **Resolved / cached content views:** GameDefinitions, SlotCatalog and ShipLoadouts now invalidate their caches when the loaded DefDatabase changes. A patch-only integration check warms the original views, replaces content, verifies patched reads and restores the original database. Audit remaining UI/static caches as their authorities move in later P2 checkpoints.
- **Resolved / frozen fares:** Cargo and passenger loads keep their departure unit value. Validation must allow a valid stored fare that differs from today's economy definition; otherwise changing a fare could invalidate an occupied ship. Content snapshots in P3 will establish the lifetime of all run balance data.
- **Observation / stale verification:** The three recorded active-suite failures came from old formation coordinates, Map/Fleet expectations, former lab output and fixed-speed assumptions. The ammunition suite also still expected three alien missiles and admitted a post-incident event without its required story flags. Correcting fixtures should preserve their underlying transaction and gameplay assertions, rather than weakening assertions to accept failures.
- **Observation / frozen setup fixtures:** The ammunition UI fixture changed simulation supply after the deployment screen had rendered, then expected the combat-only refresh to run during frozen setup. Establish empty supply before admission so the fixture tests the actual saved-supply path; hidden setup speed controls should not count as visible overlap.
- **UX observation / footer density:** Native captures at 640x360 show fuel, missile supply and the ammunition purchase packed tightly together. Current quotes fit and pointer purchases work. Consider slightly clearer separation when the HUD next changes; do not expand this content migration into a layout redesign.
- **UX concern / contradictory trip estimates:** `_render_map_details` still formats selected-trip estimates at 1x and 10x, while the actual Map has fixed 8x controls and the underway estimate uses 8x. A focused future UX change should use the current travel speed consistently.
- **Tooling concern / pack-root diagnostics:** PackLoader discovers packs inside root directories. Passing a pack directory itself can produce a warning about its `defs` child instead of loading that pack. The CLI comment calls roots "pack folders," which is easy to misread. Consider accepting both forms or reporting the expected container layout explicitly.
- **Refactor opportunity / relational validation:** Schemas validate new start/package fields, and new-run preflight rejects duplicate member IDs, unavailable fits, multiple flagships and oversized fleets. Moving reusable cross-definition checks into the loader's type-check registry would let the future Problems panel diagnose these before Playtest.
- **Imaginative proposal / starter constellation preview:** A fleet-package inspector could show the actual fitted formation and let a designer compare a convoy's fuel, cargo, lab output and early eligible research before launching. Reuse the Fleet renderer and definitions; avoid building a second fitting system.
